Ten years of one marketing site: from copy in the markup to blocks, a design system, and a CMS

Two repositories and about 20,000 commits. We moved the content out of the templates in four steps, and each step made the next one cheap. The CMS step did not change the render path, because the data contract already existed.

17,943 → 1,601lines in page template files (old repo 2022-08, new repo today)
88 → 3page files longer than 40 lines
15 → 36blocks in the library (plus 10 → 28 components)

Be honest about the last drop. In 2026, 7,443 lines of developer-owned markup (demos, editor mount points) moved out of the page files into 98 fragment files. The page files now hold only data, but the total Pug did not shrink. Tell this as "content and code now live in different files", not as "we deleted the markup".

The arc

Five stages. Each card holds what changed and the one number to use. The private notes file has the commits.

2016 – 2022 · old repo

0. The page was the content

A static site (Hexo + Pug) replaced a CMS theme. Each page template held sections with BEM classes, copy, inline <strong>, links, and pictures. The page YAML held only meta data.

  • Each copy change was a code commit by a developer. In 2021, the peak year (3,141 commits), one SEO pass alone produced dozens of commits.
  • The idea came early: in March 2017, one commit listed a reusable "module" in a page config. The commit message said that every page would do the same. It did not happen.
113 templates · 17,943 lines · 88 over 40 lines
2022 · new repo

1. A restart with blocks and components

  • Day 6: CSS layers (reset, spacing, typography) and a UI kit page, before any real page.
  • Week 2: the naming rule. A block is a page section. A component is a part inside a block.
  • Week 4: the block builder. The page YAML lists blocks, and each block reads <blockName>Data.
  • A legacy wrapper class kept old styles alive on pages that were not migrated yet.
16,474 → 7,856 lines in 7 months
2023 – 2024

2. The catalog becomes the source of truth

  • The UI kit grew into a gallery with one page for each block, built from real block data.
  • Shared parts are imported once in the base layout (one change: about 140 files, net −450 lines).
  • A global data file holds defaults, so a page sets only what is different.
plateau: about 30 blocks · about 5,700 lines
2025-08 → 2026-07

3. A design system as a theme, then as the default

  • Opt-in first: a page set a theme key in its YAML. Pages moved one at a time.
  • One "default" change: tokens to :root, utilities global, the theme class removed from markup and page configs, theme styles put into each component.
  • Then a type scale as tokens (--fs-*) and a new component structure.
link to the design-system-migration post
2026-07 → 2026-08

4. Data to a headless CMS, same render path

  • CMS → build-time fetch → cached JSON → generated page YAML → the same layout, builder, and mixins.
  • One mapper for each block turns CMS data into the <blockName>Data object.
  • A build switch turns the CMS source on or off. A hand-written page with the same slug always wins.
  • Escape hatch: developer-owned markup moved to fragment files, keyed by page folder.
  • Each block mixin got a fixed doc header: developers, schema authors, and AI agents read the same text.

Copy, URLs, and alt text sit inside the markup. One page template had 238 lines like these.

blocks:
  - bannerHero
  - info:
      source: [infoData2]
  - testimonials

bannerHeroData:
  layout: aside
  title: 'The rich text editor for every use case'
  links:
    - text: 'Start for free'
      href: '/signup'
      style: high

The page is a list of blocks plus one data object for each block. The key name bannerHeroData is the contract that the CMS uses four years later.

//- @name FAQ
//- @desc Grouped question-and-answer section; each answer is an accordion item.
//- @type Block
//- @key faqData
//- @prop {string|boolean} [title]  - Section h2, 2-6 words. Omit to inherit the site default.
//- @prop {array}          groups   - Question groups, each with a name and its own items.
//- @uses +accordion

mixin b-faq(source, externalSource)

One header, three readers: a developer, the CMS schema author, and an AI coding agent.

// mappers/faq.js — one file for each block, found automatically
export default function mapFaq( cmsBlock ) {
  return {
    key: 'faqData',                 // the same contract as in 2022
    data: {
      title: cmsBlock.title,
      groups: cmsBlock.groups.map( toGroup )
    }
  };
}

Illustrative shape, not the real file. Make sure that the post shows the idea: the mapper produces the object that the existing mixin already reads.

Open questions

The history cannot answer these. Only you can.

  1. Why did the 2017 "module in page config" idea not spread? Was there no catalog, no naming rule, or no time?
  2. What did the restart cost? Who decided on a new repo instead of a refactor, and how long did the two repos run side by side?
  3. What made the content team trust YAML edits? Did editors ever edit YAML themselves, or did developers always do it?
  4. Which blocks stay developer-only, and why?
  5. What changed for the content team after the CMS launch? Get a quote, with permission.
  6. What was your own role in each step? The post is for your CV site, so make your part clear.

Privacy check

Do a check of the draft against this list before you publish.

  • No private repository names, ticket keys, PR numbers, or commit hashes.
  • No internal URLs: preview hosts, the CMS Studio address, internal tools.
  • No colleague names. Use roles: "a front-end developer", "the content team".
  • No internal name for the design system. Write "the new design system".
  • Get approval from your employer before you name the company or the product.
  • Code examples are rewritten, not copied.
